### 简介

E04 讲了全员赋能（工具+规范），这集进入实施第三关——基础设施：给 AI 装上眼睛和记忆，让它从概率性盲读升级为确定性查证。

**核心**：工具装好了，规范也写了，可 AI 一上手还是出问题——问业务细节就瞎编，改代码看不见影响范围，骨干调走经验也带走。这集讲基础设施四件套，给 AI 装上眼睛和记忆。但先说一句反常识——小团队可以跳过，强行建基础设施是过度工程。

**你将学到**
- **业务知识 RAG**：先检索知识库再喂模型，让 AI 开卷考试——两阶段检索（多路召回→重排）+ 多租户隔离，幻觉大幅下降
- **代码知识图谱**（重头戏）：为什么用图谱不用 RAG——索引期算好关系，一次调用拿全调用链；6 阶段索引管线 + 14 个 MCP 工具 + 两条铁律（改前必跑 impact / 提交前必跑 detect_changes）
- **Skill 仓库**：团队能力复用——两层架构（公共 + 项目级）+ 业务数据入 RAG 降 Token
- **MCP 网关**：企业服务零代码封装——但 CLI 优先，能用命令行的别用 MCP
- **跳过判断**：单仓库几万行 + 无多仓库微服务 + 业务不复杂 → 直接跳过，CLAUDE.md + grep 就够

**真实案例**：某团队用代码知识图谱给 AI 装上代码眼睛，跨仓库定位调用链，累计排查 144 个生产 bug（覆盖率 80.4%）。

**适合谁看**
多仓库 / 百万行代码 / 复杂业务的大型组织（技术负责人、架构组）；小团队看完能判断我们是否需要——避免过度工程。

### 补充评论（要点拆条，可分多条发）

1. 别的教程教加东西，这集教判断要不要加——小团队可以跳过，强行建基础设施是过度工程。判断标准看三件事：代码库大不大、项目多不多、业务复不复杂。单仓库几万行内、没有多仓库微服务、业务知识不算复杂——请直接跳过本阶段，CLAUDE.md 加 grep 加良好代码组织就够。

2. AI 需要眼睛和记忆有三个痛点。第一，不懂业务——通用大模型没读过你的产品手册、内部规范，问到业务细节就幻觉，需要业务知识 RAG 给它开卷考试。第二，看不见全貌——AI 改一个函数不知道有几十处依赖它的返回类型，破坏性变更被悄悄合并，需要代码知识图谱看到爆炸半径。第三，留不住能力——某个开发者很会用 AI，调走之后经验也跟着走了，需要 Skill 仓库把高频能力沉淀成团队资产。

3. 业务知识 RAG 让 AI 开卷考试。核心是两阶段检索：第一阶段多路召回优先找全，第二阶段 CrossEncoder 重排精度提上去。还要做多租户隔离——把租户标识拼进过滤表达式，A 公司的知识 B 公司查不到，default 是全租户共享。业务 RAG 让 AI 准确回答业务问题，幻觉大幅下降。

4. 代码知识图谱是这集的重头戏。为什么用图谱不用 RAG——索引期算好关系，一次调用拿全调用链。三个好处：可靠（漏不掉上下文）/ 省 token（不用查十次去理解一个函数）/ 解放小模型（工具干了重活，对顶级模型的依赖降下来）。图谱和 RAG 不是二选一，是分层共存：确定性的调用关系走图查询，语义相似走向量搜索。索引分六步：扫描建目录、Tree-sitter 解析符号、跨文件类型传播、社区发现划功能域、执行流追踪、提取业务概念。

5. 两条铁律是基础设施落地的命脉。第一，改任何符号前必跑影响分析（impact 算爆炸半径、风险等级、直接/间接调用者数）；第二，提交前必跑变更映射（detect_changes 把 git diff 映射到受影响符号）。某团队用它跨仓库定位调用链，累计排查 144 个生产 bug，覆盖率 80.4%（相关性非因果，事后统计）。
