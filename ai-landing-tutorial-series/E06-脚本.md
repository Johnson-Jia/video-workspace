# E06 · OpenSpec + Superpowers：需求到交付一条命令（核心）

> 时长 13-15 分钟 | 横屏 16:9 | 对应教程 stage4 §1-3
>
> 合集第六集，也是规划里"最有料的一集"。E05 讲基础设施（给 AI 眼睛和记忆），E06 进入实施第四关——**闭环试点**：把"需求→代码→测试→上线"串成 AI 能端到端跑、且可中断续传的流水线。

>
> **混合设计**：方法论卡片（三堵墙 / SDD 三产物）+ **六阶段流水线可视化** + **tasks 状态机动画** + **devflow 终端演示**。

## 脚本

### 开场（复用 tutorial-opening，~20s）

### hook（~35s，反常识）
**旁白**：让 AI 写一段代码谁都会，难的是把需求到交付串成一条命令——AI 自己跑完，中间断了还能接着干。这套方法论真正的发动机不是"让 AI 写更多代码"，而是一个反常识的动作：把发现需求偏差，从改代码左移到改一份 Markdown，交付质量提升一个数量级。这集讲闭环试点，OpenSpec 加 Superpowers，教程最有料的一集。

> 视觉：深蓝底 + 大字「需求 → 交付 一条命令」逐字浮现，然后「改代码」红色质量损失 → 「改 Markdown」绿色质量可控，左移箭头。fx 用 fx-aura 静态光晕（禁划过类）。

### intro（~35s，方法论）
**旁白**：单点用 AI 容易，每个人都能让 AI 写段代码。但串成端到端流水线会撞三堵墙，这集就拆这三堵墙。先讲为什么闭环难，再讲 SDD 规范驱动怎么把纠错左移，最后用 OpenSpec 加 Superpowers 六阶段把流水线跑通，配合 devflow 一条命令编排。你能学到：怎么让 AI 端到端交付、中途断了怎么续、需求跑偏了怎么早发现、质量可控地纠正。

> 视觉：三堵墙图标横排预告 + 本集路线图（为什么 → SDD → 六阶段 → devflow）。data-reveal stagger。

### 段1 三堵墙（~80s，三卡片）
**旁白**：先讲为什么闭环难。每个人都能让 AI 写段代码，但串成端到端流水线会撞三堵墙。
- 首堵，AI 初始分析不准。你给它一句话需求，它的理解常常是偏的，照着偏的理解往下写，越写越歪。
- 第二堵，上下文断。AI 会话一中断，前面的分析、决策、进度全丢，重开等于从头再来。
- 第三堵，需求偏差晚发现。等代码写完才发现理解错了，这时候改的是代码，返工代价极大、质量难保。
- 闭环流程就是拆这三堵墙：分析不准靠规范驱动纠错左移，上下文断靠 tasks 清单断点续传，偏差晚发现靠 spec 先行先验证。

> 视觉：三卡片纵排（分析不准 / 上下文断 / 偏差晚发现），每卡图标 + 墙名 + 一句话 + 对应解法标签（SDD / tasks / spec）。data-reveal stagger，每卡进入时左侧 fx-pulse-ring 脉冲锚点。

### 段2 试点设计（~75s，决策卡）
**旁白**：闭环不是上来就全员跑，先选对试点团队、定清成功标准。
- 选谁：选意愿强的团队加业务典型的项目。别选最忙的——没空配合；别选最边缘的——结果没说服力。
- 多大：一到两个团队，每组三到八人，配一两个真实需求，跑四到八周。
- 成功标准四条：AI 代码占比达标、产出提升、质量不降、团队愿意继续用。
- 失败就止损：四到八周没明显改善就复盘，不硬推。试点的目的不是证明能行，是拿数据说话——成功有数据推广，失败有原因可查。

> 视觉：试点决策卡（选谁 / 多大 / 成功标准四条 / 止损），金边强调。四条成功标准 checklist 逐条点亮。

### 段3 SDD 三产物（~85s，卡片 + 对比，核心段）
**旁白**：拆墙的核心思想叫 SDD，规范驱动开发。把开发拆成三层产物。
- 首层 spec.md，记 WHAT——可测试的行为规格，用 WHEN THEN 格式写。它回答"做什么"。
- 第二层 plan.md，记 HOW——含完整代码的实施指南，每步前后对比加精确文件路径。它回答"怎么做"。
- 第三层 tasks.md，记 DO——可追踪的 checkbox 任务清单。它回答"做到哪了"。
- 核心价值是左移：把发现需求理解偏差，从改代码左移到改 Markdown，交付质量提升一个数量级。AI 初始理解往往不准，但改 spec 比改代码快得多。tasks 清单还带来一个 bonus——断点续传，下一段细讲。

> 视觉：三产物卡片（spec WHAT / plan HOW / tasks DO），各列格式 + 回答的问题。右侧纠错左移对比图：「改代码」红色质量损失 vs「改 Markdown」绿色质量可控，左移箭头。

### 段4 OpenSpec 三概念四命令（~80s，卡片 + 命令）
**旁白**：SDD 用 OpenSpec 落地。三个核心概念先分清。
- Spec 规格是稳定的、跨变更共享的，放 specs 目录。
- Change 变更是一次性的、做完归档，放 changes 目录。
- Archive 是变更完成后的存档。
- 四条命令覆盖全流程：explore 探索需求调查代码库，propose 生成 proposal、design、specs、tasks，apply 按 tasks 执行，archive 验证通过后归档。
- 关键一条：每次对话 OpenSpec 会自动读 specs 目录所有 spec 应用到生成代码，所以 specs 要精简，只放稳定的全局规范，一次性变更放 changes。

> 视觉：三概念卡片（Spec 稳定 / Change 一次性 / Archive 归档）+ 四命令终端窗口（explore / propose / apply / archive 逐行 reveal）。

### 段5 六阶段总览（~85s，流水线可视化，核心段）
**旁白**：团队工作流编排 OpenSpec 加 Superpowers 加代码图谱，跑六个阶段。
- 阶段一需求探索，用 brainstorming，用户可以纠正方向——这一步最关键，主动找死代码和 bug，跳过探索直接动手等于重写 bug。
- 阶段二规范生成，openspec-propose 产出 proposal、design、tasks、spec。
- 阶段三计划拆分，writing-plans 拆成可执行步骤，有代码图谱时配合 impact 和 locate。
- 阶段四 TDD 加审查，subagent-driven，跑 RED GREEN REFACTOR 循环。
- 阶段五验证，verification-before-completion，有图谱时加 detect_changes。
- 阶段六归档，openspec-archive。
- 每阶段只读当前 Stage 文件，这叫渐进式披露，省 token。

> 视觉：**六阶段流水线**（核心组件）——横向 6 节点（探索→规范→计划→TDD→验证→归档），每节点图标 + 阶段名 + skill 名（brainstorming / openspec-propose / writing-plans / subagent-driven / verification / archive），连线渐进绘制，当前节点高亮 + pulse-ring。

### 段6 断点续传（~80s，状态机动画）
**旁白**：第二堵墙"上下文断"靠 tasks 清单断点续传。
- tasks 有状态机：空框待办，in_progress 进行中，x 完成，还有 deleted 和 blocked。
- 关键在于：Claude 中途退出了，重进项目指定 change 目录，扫 tasks 的 x 标记就知道做到哪了，从下一个未完成的接着干。
- devflow 这个 skill 的恢复判定，正是扫 tasks 的 x 标记自动恢复到正确阶段。
- 真实案例：某业务组重构个人中心，十二个 Controller、两百一十一个 API、约一万五千行、一百一十个任务，全靠 tasks 清单支撑跨周断点续传。中途退出重进，看 x 标记接着干。

> 视觉：tasks 状态机动画（[ ] → [in_progress] → [x] 依次切换）+ 断点续传演示（退出 → 重进 → 扫 [x] → 续）。底部案例数据卡（12 Controller / 211 API / 15000 行 / 110 任务）。

### 段7 TDD 加子代理分工（~75s，卡片）
**旁白**：阶段四 TDD 加审查，关键是子代理分工，避免一个代理又探索又写又审的混乱。
- 四种代理各司其职：Explore 代理只搜索只读不改；实现代理按 plan 精确指令改代码；规格审查代理对照 spec 逐条验证；质量审查代理查风格、安全、命名冲突。
- TDD 循环：RED 先写测试看它失败，GREEN 写最少代码让测试过，REFACTOR 重构。
- 一条铁律：不要让 Claude 同时写代码和测试——它会写出验证错误逻辑的测试，全绿但全错。测试先行、独立验证。防偷改测试的具体护栏下集细讲。

> 视觉：四代理卡片（Explore / 实现 / 规格审 / 质量审）+ TDD 循环图（RED → GREEN → REFACTOR 三圆环）。

### 段8 devflow 一条命令（~70s，终端演示）
**旁白**：六阶段串起来靠 devflow 这个编排型 skill。
- devflow 自己不实现任何逻辑，只编排 OpenSpec 和 Superpowers，把六个阶段串成一条命令。
- 两个杀手锏：一是断点续传，中断后查文件状态自动恢复到正确阶段；二是规则覆盖，rules 目录能改写底层 skill 的默认出口，团队定制流程不用动原 skill。
- 三种模式：标准模式跑全六阶段，快速模式精简 brainstorming，迷你模式合并前三阶段适合单任务。
- 想看一个完整的多阶段 skill 怎么写，直接读 devflow 的 SKILL.md 加 stages 目录。

> 视觉：devflow 终端窗口（命令 /devflow + Stage 1-6 依次执行动画）+ 三模式卡片 + 规则覆盖示意（rules/ 改写出口）。

### 段9 工具演进：随能力做减法（~70s）
**旁白**：再补一个思想——工具不是越多越好，随能力做减法。
- 入门期：OpenSpec 加 Superpowers 结合用。前者把需求拆成规范防 AI 跑偏，后者按规范执行，新手靠框架兜底。
- 熟练期：只用 Superpowers。你已经能把需求讲清，规范思维内化了，只剩执行交框架。
- 精通期：连框架都不用，直接 Claude Code 加大模型裸交互——你就是最强的规范，你的话术就是专业的 prompt。
- 但这是个人能力的演进。团队协作、规范沉淀、新人上手场景，框架仍有价值——让能力可复制、流程可复现。精通后裸用是个人上限，不是团队标准。

> 视觉：三阶段阶梯图（入门 OpenSpec+Superpowers → 熟练 Superpowers → 精通 裸 Claude Code），逐级工具递减、能力递增。顶端金句「你就是最强的规范」卡，fx 用静态光晕强调。

### CTA（~30s）
**旁白**：闭环试点是这套方法论真正的核心发动机——纠错左移把交付质量提一个数量级，断点续传让 AI 真正能端到端跑。下集讲测试侧的闭环：怎么防 AI 偷改测试，加四个真实案例，从单点修复到大规模迁移。合集还有七集，点关注不走丢，教程仓库在评论区。最后问你：你的团队，AI 写代码能跑通端到端闭环吗？

> 视觉：合集标识 + E07 预告卡（防偷改测试 + 真实案例）+「关注不走丢」CTA。

## 核心组件设计

### 六阶段流水线（段5，核心）
```html
<div class="pipeline">
  <div class="stage-node" data-stage="1">探索<br>brainstorming</div>
  <!-- 6 个节点：探索/规范/计划/TDD/验证/归档 -->
  <svg class="pipeline-edges"><line ... class="edge active"/></svg>
</div>
```
CSS：节点方形 110px + 染色（阶段渐变，冷→暖，同色系禁白端点），当前节点 ring 发光（box-shadow 同色系，禁白）。连线 SVG stroke 同色系，渐进绘制（dashoffset 动画，非划过类 fx）。
GSAP：节点依次出现（scale 0→1 stagger）→ 连线渐进 → 当前节点高亮 pulse-ring。

### tasks 状态机（段6）
三状态卡片（`[ ]` 待办 / `[in_progress]` 进行 / `[x]` 完成），GSAP 依次切换高亮 + 打勾动画。底部断点续传演示（退出图标 → 重进 → 扫描 `[x]` → 续行箭头）。

### devflow 终端（段8）
复用 E04/E05 终端组件（深底 #0a0a0a + 标题栏 + 红黄绿圆点）。命令逐字打字（data-typewriter）+ Stage 1-6 依次执行输出 fade-in（data-reveal）。

### SDD 三产物 + 左移对比（段3）
三卡（spec WHAT / plan HOW / tasks DO）+ 右侧左移对比（「改代码」红质量损失 → 「改 Markdown」绿质量可控，左移箭头）。

## 制作提示（继承 E05 + E06 差异）

| 项 | 规则 |
|----|------|
| **双版本输出** | 版本1 `E06-final.mp4`（各段 output.mp4 concat 含开场）/ 版本2 `E06-final-pierce.mp4`（output_no_bgm concat + BGM 一首贯穿 volume **0.60** + 开头拼开场）|
| **BGM pierce** | clean-corporate 或 warm-editorial 同系列 acrossfade d=2 拼接到 ~720s + stream_loop + volume **0.60** + 头淡入 2s 尾淡出 3s + Mastering -14 LUFS + 每首 loudnorm I=-20 |
| bg | dark_cipher（代码矩阵，契合"规范驱动"；换掉 E05 的 hex_grid 做合集内差异）|
| 字体 | 渐变端点亮（同色系禁白）+ text-shadow 极淡 0.08（rgba(30,41,59,0.08)，禁发光 `0 0 Xpx`）|
| 清晰度 | concat crf 14（不是 18）+ 各段 stereo 统一（-ac 2，防 mono↔stereo 声道乱跳）|
| 终端/代码窗口 | 深底 #0a0a0a + 等宽字 JetBrains Mono + 打字动画 GSAP |
| 多音字 | 转→转型 / 藏→隐藏 / 2→两 / 12→十二（tutorial.md 规则）|
| 禁"第一" | 用"首要 / 起手 / 其一" |
| 创作指令禁泄露 | subagent prompt 的创作约束不进 narration/creative，只写教程知识 |
| 段间衔接 | 各段尾不预告下段、首不回顾上段，靠内容逻辑自然过渡 |
| fx 规则 | 禁划过类（scan/stream/beam），用静态/脉冲（aura/pulse-ring/particle）|
| fx 冷色优先 | 教程 fx 冷色（蓝/紫/绿）沉稳；暖色 alpha≤0.22（E03 事故）|
| 字数 | 各段 150-250 字（对应 60-85s）|
