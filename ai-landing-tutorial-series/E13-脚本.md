## 脚本

### 开场（复用 tutorial-opening，~20s）

### hook（~30s，实操）
**旁白**：AI 写测试最大的坑，是虚假通过。AI 幻觉让测试脚本看着跑通了，实际根本没验证到点子上，你以为是绿灯，上线就翻车。这集跑 ai-test-frame，一个最小可运行的 AI 自动化测试框架，开箱就跑。核心思路：AI 只负责生成测试代码，运行期全是确定性的数据驱动，零 AI，根治虚假通过。

> 视觉：深色底 + 大字「虚假通过」红叉 + 「ai-test-frame 开箱跑」+ 测试报告生长。fx-aura 静态光晕（冷色优先）。

### intro（~30s，方法论）
**旁白**：这集是合集收官集，讲 AI 自动化测试实操。你能学到五个关键思想：AI 只生成不执行、数据与代码解耦、注册中心模式、软断言、变量传递。对应框架八个文件，每个文件一个核心模块，架构清晰，开箱跑通。

> 视觉：5 关键思想 data-reveal stagger（AI 只生成 / 数据代码解耦 / 注册中心 / 软断言 / 变量传递）。

### 段1 架构总览（~55s，架构图，核心段）
**旁白**：先看框架八个文件的全景。registry 注册中心，装饰器登记用例类型。assertions 软断言，失败不中断加截图加收集。base_page 测试基类，封装通用操作和通用定位。runner 数据驱动调度器，读用例按类型路由。handlers 具体业务处理器，这里只放商品管理一个示例。main 执行入口，开浏览器跑用例汇总。data 用例数据，运营在这里编步骤。site 被测页，自带极简商品管理页开箱跑。八个文件对应五个核心思想。

> 视觉：8 文件架构图（nest_tree 目录树）+ 每文件一句话作用。

### 段2 注册中心（~55s，代码，核心段）
**旁白**：注册中心是这套框架的灵魂。写一个装饰器 register，把方法登记进全局表，调度器按类型自动取。关键细节，类引用延迟解析——装饰器执行时类还没定义完，那时取会拿到空，所以类引用放到调度器创建实例时再解析。好处是，新增一个业务模块，写完注册，调度器自动发现，零改调度器代码。这是企业级测试框架提炼出来的核心模式。

> 视觉：registry.py 代码片段（@register 装饰器）+ 调度器按 type 取 handler 流程图。

### 段3 数据驱动（~55s，代码，核心段）
**旁白**：数据与代码彻底解耦。用例在 data 目录，是纯粹的步骤 JSON，运营在这里编，不碰代码。代码在 handlers 目录，是具体业务实现。调度器 runner 读用例，按 type 路由，基础操作走字典，模块操作走注册中心。还有变量传递，下划线 save_as 保存，花括号变量名引用，步骤间用例间都能传。运营编步骤，开发写 handler，分工清晰。

> 视觉：data/cases.json（4 条用例 3 跑 1 关）+ runner 按 type 路由 + ${变量} 传递示意。

### 段4 软断言（~50s，对比，核心段）
**旁白**：软断言对比硬断言。硬断言就是 assert，一条失败立刻停，后面的验证全跑不到。软断言相反，失败不抛异常不中断，自动截图，收集结果，一条用例的多个验证都跑完，全记进报告。更贴近记录问题，不是一错就停。输出用纯文本标记通过失败，兼容命令行的编码，不靠表情符号。

> 视觉：对比（硬断言：失败即停 ❌ / 软断言：失败截图+继续+汇总 ✓）+ 终端 [通过]/[失败] 输出。

### 段5 AI 只生成不执行（~55s，方法论，核心段）
**旁白**：这是整套框架最关键的思想。AI 只生成，不执行。handler 由录制加 AI 转换加人审，在编码期产出。运行期是确定性的数据驱动调度，零 AI。为什么这么设计？规避幻觉。AI 直接运行测试，可能幻觉出一个虚假通过——它以为验证了，实际没有。AI 只负责生成代码，人审通过后，运行期全确定性执行，根治虚假通过。

> 视觉：流程（录制 → AI 转换 → 人审 = 编码期产出 handler / 运行期零 AI 确定性执行）+ ⛔ 虚假通过红叉。

### 段6 实跑演示（~55s，终端演示，核心段）
**旁白**：开箱跑一遍。确认进到 ai-test-frame 目录，装依赖，装浏览器内核，跑 main。Playwright 打开自带的商品管理页，按用例跑，新增商品验证列表出现，终端输出断言汇总：通过两个，失败零个。第四条用例开关是关闭，自动跳过。整个流程确定性执行，没有 AI 在运行期插手。

> 视觉：terminal（cd ai-test-frame → pip install → playwright install chromium → python main.py → 通过2 失败0）+ scan_line 扫输出。

**[终端演示 reveal]**
```
cd demos/ai-test-frame
pip install -r requirements.txt
playwright install chromium
python main.py
→ 通过 2, 失败 0
```

### 段7 换你的系统（~45s，步骤）
**旁白**：demo 自带的商品页是为了开箱跑。真实用的时候四步改造。其一，改 base_page 的定位，匹配你系统的界面，保持通用定位策略。其二，改 main 的跳转地址，指向你的系统，加登录。其三，照 test_product 的写法，为你的业务写更多 handler。其四，在 data 编用例，生产可用表格替代 JSON，数据驱动思想一致。

> 视觉：4 步改造卡（改定位 / 改地址加登录 / 写 handler / 编用例）。

### CTA（~25s）
**旁白**：AI 自动化测试的核心，是让 AI 只生成、确定性执行，把幻觉挡在运行期之外。这套 ai-test-frame 开箱跑通，换你系统四步改造。十三集合集到这就全部完结，从思想转变到落地实操，一条龙走完。点关注，教程仓库在评论区。最后问你：你的项目，测试现在是怎么跑的？

> 视觉：合集标识 + 13 集完结徽章 + 关注 CTA + 中性提问。

## 核心组件设计

### 8 文件架构树（段1，核心）
nest_tree 目录树（ai-test-frame/ 下 registry/assertions/base_page/runner/handlers/main/data/site）+ 每文件一句话作用。

### 注册中心流程（段2，核心）
registry.py @register 代码片段 + 调度器按 type 取 handler 流程（type → registry.get → 延迟解析类 → 创建实例 → 调用方法）。

### 软断言对比（段4，核心）
双卡对比（硬断言失败即停 ❌ / 软断言失败截图+继续+汇总 ✓）+ 终端 [通过]/[失败] 纯文本输出。

### AI 只生成不执行流程（段5，核心）
横向流程（编码期：录制 → AI 转换 → 人审 → handler / 运行期：零 AI 确定性执行）+ ⛔ 虚假通过红叉。
